# GV Workspace: fresh implementation

New implementation, created from scratch on 27 September 2026 without reusing the previous CRM code. Separately authorized imports may exist in private development databases. This is an incremental build, **not the complete requirements document or a production release**.

## Run locally

Node 24+, `npm ci`, then `npm run dev`. Open `http://127.0.0.1:4320` and choose a clearly labelled sample identity. A newly seeded default database contains fictional fixtures under ignored `.data/workspace`. **Authentication mode does not classify data:** an existing database can contain imported real records. Never reset/reseed or run mutating QA against it. The previous app is not used or changed.

See the [9 October UX/build-readiness review](docs/UX-REVIEW-2026-10-09.md) for all 36 navigation destinations, prioritized acceptance criteria, functional gaps and execution order. Review completion does not mean implementation or release completion.

`npm run verify` runs type checks, API/ledger tests, production client build and browser tests. Local browser tests use installed Chrome with a separate in-memory database on port 4322. CI uses Playwright Chromium. `GV_TEST_DATABASE_URL` optionally runs integration tests against an empty, disposable loopback PostgreSQL database named `gv_workspace_test`; never point tests at live data.

## Working slice

- Separate tenants, memberships, legal entities and shared customer/vendor companies.
- Contacts with dated many-to-many company associations, preserving old project links.
- Leads convert to linked deals without re-keying.
- Editable, version-checked contact and company profiles: secondary emails and typed phones, addresses, tags, lifecycle/source, consent evidence, currency and servicing-entity preferences. Primary/secondary contact emails share tenant-wide uniqueness. Employer changes retain dated affiliations and old commercial snapshots; profile preferences never silently change a document's issuing entity.
- Lead detail and qualification states, disqualification reasons, reopening with a next action/date, and conversion retaining linked history. Assigned tasks have due dates, priorities, completion/reopening, a filtered Tasks workspace and a My day queue. Manual calls, meetings, emails and notes appear on linked contact/company/lead/deal timelines; email references are explicitly manual, not proof of sending or synchronization. Task assignment respects active membership and root-record visibility.
- Named quote alternatives with immutable revisions. Any specific version can be accepted; newest never automatically wins.
- Accepted quote to partial or full invoice drafts, explicit numbered issue, cash, income-tax withholding and customer-withheld sales tax (its own receivable, so a payment may be entirely withheld), partial payments, draft cancellation and unpaid invoice reversal. Each invoice owns its immutable amounts and allocated line/tax snapshot; old invoice amounts are preserved by a tested migration.
- Projects from the exact accepted quote, retaining the client/contact, deal and explicitly confirmed issuing entity. Project dates, status and PKR cost budgets are versioned and audited. Planned milestones and invoice drafts reserve the contract subtotal, preventing overbilling; cancelling/voiding releases the invoice allocation. Advance invoices defer net revenue until finance explicitly records delivered work, with dated, immutable partial recognitions.
- Project profitability from posted ledger entries: earned revenue, costs, exchange result, cash collected, withholding, outstanding receivables, deferred revenue and budget variance. Linked vendor bills accrue costs once; payments do not duplicate them. Equipment and prepayments stay outside expense. Existing deal-linked documents are included when a project is created.
- Manual PKR/USD/AED/EUR/GBP transaction currencies, PKR base, fixed document exchange rates, realised FX gain/loss on settlement.
- Invoice-based partial/full credit notes with original-line tax allocation, explicit earned/deferred treatment, applications to same-customer/entity/currency invoices, recorded customer refunds with FX, and dated immutable reversals. Credits reduce receivables only when applied; unused credits remain a separate liability. Historical ageing, cash flow and project profitability include the effects. Original invoices are preserved; credits do not silently reopen fixed-contract billing allocation.
- Recurring invoice and paid-expense schedules: weekly/monthly/quarterly/yearly anchored dates, explicit timezone, end/count limits, pause/resume/stop, versioned future edits and an audited occurrence history. A 60-second server worker catches up in batches of 12 due cycles per profile, with manual generation and explicit skip actions. Invoice cycles create unposted drafts; expense cycles require payment review before posting. Retry/row-lock protection prevents duplicate cycles. Revoked/non-finance creators cannot run background generation. Recurring service contracts use a separate accepted deal rather than bypassing fixed-project budgets.
- Paid general/project expenses, separate charts/ledgers per entity, trial balance movements, journal drill-down, transaction locks, immutable audit records.
- Vendor bills with editable drafts, submission, retained amount-tiered Finance/Admin approval policies, duplicate checks and explicit entity/project links. Shared bills/PO workflows support named people, financial roles/custom profiles, ordered any/all steps, PKR thresholds and creator exclusion. Submission snapshots retain rules/reviewers, current access is rechecked on review, and only final bill approval posts the ledger; final PO approval issues the order without emailing or posting. Settings drafts recover within the browser tab. Existing bill policies remain until shared rules are configured. Partial payments support withholding, bank fees and realised FX; dated payment reversals and unpaid-bill voids preserve the original ledger history.
- Purchase orders with recoverable drafts, approval, partial bill conversion and immutable conversion allocations. Vendor credits support applications, recorded refunds and dated reversals.
- Bank transactions record money in or out with no invoice, bill or expense behind it — owner drawings and capital, salaries net of tax withheld, partner reimbursements, interest and charges — allocated across ordinary accounts that must explain the full amount. Control accounts and other bank accounts are refused, locked and reconciled periods are respected, entries are immutable and audited, and they appear as book lines for reconciliation. Transfers between two bank accounts are not built yet.
- One recorded vendor payment can allocate several approved bills for the same vendor, legal entity and currency, including withholding and a single bank fee. One bank entry reconciles the payment; historical ageing, statements, cash flow and project profitability retain per-bill carrying amounts. Whole-payment reversal restores every allocation. These records do not initiate bank transfers.
- Single-bill and grouped vendor payments offer a printable remittance advice with exact per-bill cash/withholding allocations and separate bank charges. Reversed records are clearly marked. Advice uses current directory details and is not bank-transfer proof or a statutory withholding certificate; it is not automatically emailed.
- Recurring vendor bills have a separate Purchases workspace: recoverable creation/edit drafts, anchored weekly/monthly/quarterly/yearly dates, timezone/end/count limits, pause/resume/stop, explicit due-cycle skipping and immutable cycle snapshots. Manual generation creates the next draft; the worker catches up at most 12 cycles per pass, committing each independently. Duplicate warnings and locked periods stop the cursor and show a review error. Generated bills still require normal submission and approval; vendor invoice references and foreign exchange rates must be reviewed. Future template edits never reprice prior drafts.
- Vendor directories and payable balances by entity and transaction currency. Base-currency balances use historical carrying amounts; period-end FX revaluation is not implemented.
- Vendor purchase advances have recoverable capture drafts, safe retry identity, approved-bill applications, recorded unused refunds and exact dated reversals. Historical prepayment carrying differences adjust original purchase costs rather than settlement FX. Cash, withholding and fees remain separate; capital advances retain investing cash classification. Ageing, vendor statements and project costs include applications and reversals. These are purchase prepayments, not refundable security deposits or loans; they do not send payments or adjust statutory withholding certificates.
- Ledger-based accrual P&L, balance sheet, indirect cash flow for classified posting types, opening/movement/closing trial balance, historical receivable/payable ageing with ledger-control reconciliation, account drill-down, CSV and browser print/PDF. Reports use a consistent transaction snapshot. Combined entity reports are labelled as aggregates, not consolidated statements.
- Named PKR bank accounts with explicit verified opening balances/offsets, account selection on receipts/vendor payments/expenses, validated CSV statement previews/imports, grouped matches, auditable undo before completion, reconciliation and carried-forward uncleared items. Reconciled bank dates reject backdated postings; imports and matches never create income/expenses.
- One-time, per-entity PKR cutover preview for a closing trial balance, custom chart accounts, unpaid customer invoices and vendor bills. CSVs are validated before any write; debits/credits, bank openings and AR/AP controls must reconcile. Administrator confirmation posts immutable opening documents and ledger entries atomically, clears account 3900 to zero and locks dates through cutover. Test with fictional data and accountant review before real migration.
- Transaction-level RLS, own-record sales filtering, role checks, session cookies, origin/CSRF validation and retry protection for financial postings.
- Responsive React UI with light/dark/high-contrast themes and side-panel forms.
- Organization creation/switching, administrator-managed invitations, member roles, access removal/restoration and session revocation. Invitation links are shared manually, not emailed.
- Configurable OIDC authorization-code sign-in with PKCE, nonce, browser-bound state, signature/issuer/audience checks and verified-email invitations. Separate sample and identity-enabled databases; sample sessions cannot authenticate to the hosted adapter.

## Identity-enabled staging adapter

`npm run dev` remains loopback-only development access. Default seeding creates fictional records, but development authentication does not prove an existing database is fictional. `GV_SKIP_SEED=1` preserves approved imported data without seeding; `GV_DISABLE_RECURRING_WORKER=1` pauses automatic schedule generation. Never run mutating QA against a real-data preview. A separate `npm start` entry point serves the built client and requires an HTTPS public origin, a new PostgreSQL database and a configured OIDC provider. It does not run Vite or expose sample login routes. The provider must support authorization-code/PKCE and supply a verified email; automatic email-based account linking is deliberately disabled. Provider provisioning and real-account verification have **not** been performed.

See `.env.example` for names only; supply real secrets through a secret manager, not Git. Register the exact `/auth/callback` URL with the provider. Review/back up the target before explicitly applying migrations with `GV_MIGRATION_TARGET=oidc npm run db:migrate`. Serving verifies migration checksums and refuses a sample-marked database. Put TLS and a correctly configured reverse proxy in front of the loopback listener; preserve the configured Host. Proxy-aware/distributed rate limiting and deployment security review remain required before multi-user hosting.

Local tests exercise the real OIDC protocol library against a disposable signed-token issuer, including bad signatures, wrong nonce/audience/issuer, expired requests, replay, unverified email and session separation. This is not evidence of a live identity-provider deployment.

## Deliberate limits / next work

Core sales and payable actions use a shared capability policy, with a role matrix in Team & access. Administrators can create organization-scoped custom roles from Finance, Sales or Viewer templates that only remove permissions; assignments/edits are versioned, audited and end affected sessions. Commands pass a server capability gate and unknown actions fail closed. Capability-driven client gates and member legal-entity grants exist in the reviewed branch; contacts/companies stay shared. Entity allowlists are not different roles per entity. Retained bill tiers and shared bills/PO approvals are implemented; approvals for other document types, delegation, escalation and notifications remain outstanding. Branch implementation does not prove open PRs merged or release validation.

Different roles per entity, extended onboarding, SaaS subscriptions, contact import/merge, configurable custom fields/pipelines, task recurrence/reminders, complete multi-document approvals, staff reimbursements, billable-cost invoicing, broader attachments, inventory, live bank integrations, foreign-currency bank accounts, bank transfers, tax/WHT certificates, advanced/comparative reports, full portals, email/calendar sync and other requirements remain. Quotes are manually marked shared; nothing is emailed. No statutory tax configuration is assumed. Base currency is PKR; broader precision/rate providers remain open. Bank reconciliation reopening remains; month-close reopening is administrator-controlled and audited. Basic service desk and SaaS controls include outstanding P1 requirements, not only later parity.

Project limits: one fixed-contract project per accepted deal, finance/admin access, partial amounts spread over remaining quoted lines with exact remaining tax allocation. No scope-change orders, project team/tasks/timesheets, time-and-materials or full retainer drawdown, WIP valuation, overhead allocation or automated revenue recognition schedules yet. Profitability is all recorded dates, not a selectable historical project report. Budgets are PKR and compare posted costs; draft purchase commitments are not accrued. Advances use the agreed quote's tax treatment; this is not jurisdiction-specific retainer/tax-compliance certification. Revenue recognitions require delivery evidence and cannot yet be reversed in the UI; a recognised advance cannot be voided.

Billing limits: credits currently originate from issued invoices, not standalone opening credits. Refunds record money already returned; they do not transfer funds or adjust withholding certificates. Schedules generate drafts only, never auto-send, auto-charge or auto-post. Expense schedules are PKR paid-expense templates, not recurring vendor bills. Start date/frequency/timezone are fixed; use a new contract to change them. Generated documents keep their snapshots and cannot be regenerated for the same cycle after cancellation. Review template rates before due cycles; no market-rate feed or draft repricing is provided. The worker requires a running server and active finance creator; it is not an external durable job queue or a deployment-readiness claim.

Report limits: no cash-basis statements, consolidated eliminations, period-end FX revaluation, XLSX export, scheduled reports or statutory tax reports. Cash flow fails visibly for unclassified cash posting types (including opening-balance setup within the selected period); it does not silently guess a classification. Cutover currently accepts PKR documents only, requires companies and named bank accounts to exist first, rejects entities with operational entries, and has no live Zoho connector or general journal import. Statement imports currently require exact Date/Description/Reference/Amount CSV columns, up to 500 rows/100 KB. Historical unassigned bank/cash postings are preserved, not silently moved into new accounts. Larger bank/report datasets still need pagination/performance work.

The client list snapshot is appropriate for this small increment, not yet paginated for production-scale tenants. Production runtime/control DB privilege separation, live identity-provider configuration/validation, background jobs, backups, observability, performance/security reviews, accountant sign-off and user acceptance remain release gates. The local preview entry point refuses production mode. Disposable PostgreSQL integration tests have now passed on GitHub Actions; this is not production hosting, live-data validation or release sign-off.
